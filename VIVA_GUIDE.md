# Project Evaluation II - Viva Guide

## 1. Where We Added Things & How They Work

### A. MongoDB Integration & Data Syncing
* **Where:** `server/models/` (`UserModel.js`, `CourseModel.js`) and `server/controllers/` (`studentController.js`, `courseController.js`).
* **How it works:** We migrated the application from using temporary browser storage to persistent MongoDB. When you create a Student or Course from the React frontend, it sends a payload (like `student_id`, `first_name`, `department`). The backend controllers intercept this, map the fields perfectly to the Mongoose schema, save it, and return the data formatted exactly how the React tables expect it (e.g. converting MongoDB's `_id` into `id`). We used `{ strict: false }` in the Mongoose schemas so that any extra fields the frontend sends (like GPA or Credits) are flexibly saved without breaking the database.

### B. Automated Email & Temporary Password System
* **Where:** `server/controllers/studentController.js` and `server/utils/emailService.js`.
* **How it works:** When an admin adds a new student, the backend generates a temporary password using a specific format (e.g., `Stu-DJY615C`). The backend hashes this password using `bcrypt` and stores the secure hash in MongoDB. Simultaneously, `nodemailer` (using your configured Gmail App Password in the `.env` file) sends a beautifully formatted HTML email to the student with their plaintext credentials.

### C. Mandatory "First-Login" Password Change Flow
* **Where:** `server/models/UserModel.js`, `server/controllers/authController.js`, and the frontend Router (`layout.jsx`, `ChangePassword.jsx`).
* **How it works:** Every new student is created with a `firstLogin: true` flag in MongoDB. When they log in using the temporary password emailed to them, the JWT authentication middleware detects this flag. Instead of letting them into the dashboard, it forcefully redirects them to the `/change-password` page. Once they set a new permanent password, the backend hashes the new password, flips `firstLogin` to `false`, and grants them full dashboard access.

### D. Resolving Authentication Conflicts (Google vs Local)
* **Where:** `server/controllers/authController.js` (inside the `/register` endpoint).
* **How it works:** Previously, if a user logged in with Google OAuth first, MongoDB created an account with a `googleId` but no password. If the admin later tried to assign them a password, it threw a "User Already Exists" error. We upgraded the controller to gracefully handle this by simply appending the newly generated hashed password to the *existing* Google account, perfectly bridging the gap between OAuth and Local authentication.

## 2. Potential Viva Questions & How to Answer Them

**Q1: How are you securing student passwords in your database?**
**Answer:** Passwords are never stored in plain text. Before saving a password (whether it's the temporary one generated by the admin or a permanent one set by the user), it is encrypted using the `bcrypt` library with a salt round of 10. Even if the database is compromised, the passwords are secure hashes.

**Q2: Can you explain the complete flow of onboarding a new student?**
**Answer:** Yes. The admin fills out the student form. The backend dynamically generates a temporary password (e.g., `Stu-A1B`), hashes it, and saves the user to MongoDB with a `firstLogin: true` flag. It then uses `nodemailer` to email the plaintext temporary password to the student. Upon their first login, the system detects the `firstLogin` flag and immediately locks them out of the dashboard until they create a permanent, secure password via the Change Password screen.

**Q3: How did you ensure the new MongoDB backend didn't break your existing React frontend tables?**
**Answer:** The React frontend expects very specific field names (like `id` instead of MongoDB's `_id`, or `first_name` and `last_name` instead of a single `full_name`). Inside my backend controllers (`studentController` and `courseController`), I intercept the MongoDB documents, use `.toObject()`, and dynamically map the fields to match exactly what the React components expect before sending the JSON response. 

**Q4: Why did you use `{ strict: false }` in your Mongoose schemas?**
**Answer:** Because the frontend forms collect a wide variety of dynamic data (like address, GPA, academic year, credits), setting the schema to `{ strict: false }` allows MongoDB to flexibly store these extra fields without needing a rigidly locked schema. This makes the system scalable and highly adaptable to future frontend changes.

**Q5: How does the system handle someone logging in with Google OAuth versus a standard Email/Password?**
**Answer:** The system supports dual authentication. If a user logs in via Google, they are saved using a unique `googleId`. If they are later assigned a local password, the database just updates that specific document. During login, the `authController` checks if the provided credentials match either the local `studentId/email` combo or the OAuth token, and issues a unified JSON Web Token (JWT) regardless of the login method.
